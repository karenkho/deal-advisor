# Feature Pattern Library

## Login with MFA

- **Type:** integration (when OTP via SMS/email provider) or screen_crud (TOTP app only)
- **Typical size:** M
- **Description:** Users sign in with username/email and password and confirm with a one-time code sent by SMS/email or generated by an authenticator app.
- **Acceptance criteria:**
  - Given a registered user with MFA enabled, When they enter valid credentials, Then the system sends a 6-digit code valid for 5 minutes and grants access only after the code is entered.
  - Given five consecutive failed attempts, When the user tries again, Then the account is locked for 15 minutes and the attempt is logged.
- **Variations that change size:** SSO with enterprise IdP instead (L); MFA optional per role (+0); risk-based MFA by device/location (L).

## Self-registration with email verification

- **Type:** screen_crud
- **Typical size:** M
- **Description:** External users create their own account, verify their email, and accept terms and privacy consent.
- **Acceptance criteria:**
  - Given a new user, When they submit the registration form, Then a verification link is emailed and the account stays inactive until the link is used.
  - Given an email already registered, When a user registers with it, Then the system rejects it without revealing account details.
- **Variations that change size:** identity verification with ID upload and staff approval (L); government ID / KYC API check (L).

## Role-based access control (RBAC)

- **Type:** admin_config
- **Typical size:** L
- **Description:** Administrators define roles and assign permissions per module and action; menus and actions are shown according to role.
- **Acceptance criteria:**
  - Given a user with the "Viewer" role, When they open a record, Then edit and delete actions are not available and direct API calls are rejected.
  - Given an administrator, When they change a role's permissions, Then the change applies at the user's next request and is written to the audit trail.
- **Variations that change size:** fixed roles only, no admin screen (S, part of Foundation); data-scope restrictions by branch/region (XL).

## User administration

- **Type:** admin_config
- **Typical size:** M
- **Description:** Administrators create, deactivate, and reset staff accounts and assign roles and offices.
- **Acceptance criteria:**
  - Given an administrator, When they create a staff account, Then the user receives an activation email and must set a password at first login.
  - Given a deactivated user, When they attempt to log in, Then access is denied.
- **Variations that change size:** bulk user import from CSV (+1 tier); sync from Active Directory (L integration).

## Audit trail

- **Type:** admin_config
- **Typical size:** M
- **Description:** Every create, update, delete, approval and login is recorded with who, when, what changed (before/after), and source IP; authorized users can search the log.
- **Acceptance criteria:**
  - Given any record update, When it is saved, Then an audit entry stores the user, timestamp, field changes, and IP address.
  - Given an auditor, When they filter the audit log by user and date range, Then matching entries are listed and exportable to CSV.
- **Variations that change size:** tamper-evident (hash-chained) log (L); retention and archiving rules (+1 tier).

## Single-level approval

- **Type:** workflow
- **Typical size:** S
- **Description:** A submitted record is approved or rejected by one role with remarks.
- **Acceptance criteria:**
  - Given a submitted request, When the approver approves it, Then the status becomes "Approved" and the action is recorded in the history.
  - Given a rejection, When the approver rejects without remarks, Then the system requires remarks.
- **Variations that change size:** return-for-correction loop (M).

## N-level approval workflow

- **Type:** workflow
- **Typical size:** L
- **Description:** Requests pass through two or more approval levels with routing rules, return-for-correction, delegation and SLA escalation.
- **Acceptance criteria:**
  - Given a request above the amount threshold, When level 1 approves, Then it routes to level 2; otherwise it is final.
  - Given an approval pending past its SLA, When the SLA expires, Then the request escalates to the next approver and both are notified.
  - Given an approver on leave, When delegation is active, Then the delegate can act and the history shows "on behalf of".
- **Variations that change size:** fixed 2 levels without routing (M); admin-configurable workflow designer (XL).

## Email notification

- **Type:** notification
- **Typical size:** S
- **Description:** Event-triggered emails from fixed templates (e.g., submission received, approved).
- **Acceptance criteria:**
  - Given a request is approved, When the status changes, Then the requester receives an email with the reference number within 5 minutes.
  - Given the email provider is unavailable, When sending fails, Then the system retries and logs the failure.
- **Variations that change size:** admin-editable templates (M); multiple languages (+1 tier).

## SMS notification

- **Type:** notification
- **Typical size:** M
- **Description:** Event-triggered or scheduled SMS through an SMS aggregator API with delivery log.
- **Acceptance criteria:**
  - Given a mobile number on file, When an appointment is confirmed, Then an SMS is sent with date, time and reference number.
  - Given a delivery failure report, When the aggregator returns an error, Then the log shows the failure and the message is retried once.
- **Variations that change size:** two-way SMS (reply to confirm) (L); bulk campaigns (XL).

## CSV / Excel import

- **Type:** screen_crud
- **Typical size:** M
- **Description:** Authorized users upload a spreadsheet in a published template; the system validates rows and imports valid ones.
- **Acceptance criteria:**
  - Given a file in the template, When it is uploaded, Then the system shows a preview with row-level validation errors before import.
  - Given confirmed import, When rows are valid, Then they are created and a summary of imported and rejected rows is downloadable.
- **Variations that change size:** update-or-insert matching on keys (+1 tier); scheduled SFTP drop (integration M).

## Standard tabular report

- **Type:** report_dashboard
- **Typical size:** S
- **Description:** A filtered list report exportable to Excel/CSV.
- **Acceptance criteria:**
  - Given filters for date range and status, When the user runs the report, Then matching rows display with totals.
  - Given results, When the user exports, Then an Excel file with the same columns downloads.
- **Variations that change size:** PDF with official layout and signatories (M).

## Printable official form / certificate

- **Type:** report_dashboard
- **Typical size:** M
- **Description:** Generate a PDF document (permit, certificate, statement) from record data with official layout, QR code and reference number.
- **Acceptance criteria:**
  - Given an approved permit, When the applicant downloads it, Then a PDF with the official layout, QR code and permit number is generated.
  - Given a QR code scan, When the verification page is opened, Then it shows whether the document is valid.
- **Variations that change size:** digital signature with certificates (L).

## KPI dashboard

- **Type:** report_dashboard
- **Typical size:** L
- **Description:** Management dashboard with 4–8 KPI widgets, trend charts and date filters, scoped to the user's role.
- **Acceptance criteria:**
  - Given a manager, When they open the dashboard, Then KPIs for their office are shown for the current month by default.
  - Given a date range, When it is changed, Then all widgets refresh consistently.
- **Variations that change size:** 1–3 simple counters (M); near-real-time from multiple sources (XL).

## Payment gateway integration

- **Type:** integration
- **Typical size:** L
- **Description:** Online payment of fees through a payment gateway with redirect/checkout, webhook confirmation and daily reconciliation.
- **Acceptance criteria:**
  - Given an unpaid assessment, When the user pays successfully, Then the gateway callback marks it paid and an official receipt number is issued.
  - Given a callback not received, When the daily reconciliation runs, Then mismatches are listed for finance review.
- **Variations that change size:** multiple gateways/e-wallets (XL); pay-over-the-counter reference code only (M).

## Government API integration

- **Type:** integration
- **Typical size:** L
- **Description:** Verification or submission to a government agency API (e.g., business registry, tax ID validation) with certificates, onboarding and IP allow-listing.
- **Acceptance criteria:**
  - Given a registration number, When the user requests verification, Then the system calls the agency API and stores the response with timestamp.
  - Given the agency API is down, When verification fails, Then the record is marked "pending verification" and retried later.
- **Variations that change size:** no sandbox or documentation available (XL).

## E-invoicing submission

- **Type:** integration
- **Typical size:** XL
- **Description:** Transmission of electronic invoices to the tax authority's e-invoicing system in the prescribed format, with acknowledgment handling.
- **Acceptance criteria:**
  - Given a finalized invoice, When it is transmitted, Then the acknowledgment ID is stored and shown on the invoice.
  - Given a rejection, When the tax system returns errors, Then the invoice is flagged for correction with the error details.
- **Variations that change size:** via an accredited third-party provider with a clean API (L).

## Document upload and management

- **Type:** screen_crud
- **Typical size:** M
- **Description:** Upload of supporting documents against a requirements checklist, with type/size validation, preview and versioning.
- **Acceptance criteria:**
  - Given a checklist of required documents, When the applicant uploads a PDF over 10 MB, Then the upload is rejected with a message.
  - Given all required documents, When they are uploaded, Then the checklist shows complete and submission is enabled.
- **Variations that change size:** virus scanning and OCR (L); staff-side document verification step (+1 tier).

## Search and filter

- **Type:** screen_crud
- **Typical size:** S
- **Description:** Keyword search and filters on a main list with sorting and pagination.
- **Acceptance criteria:**
  - Given 10,000 records, When the user searches by name, Then results return within 3 seconds with pagination.
  - Given filters for status and date, When applied together, Then only records matching both are shown.
- **Variations that change size:** full-text search across documents (L).

## User self-service profile

- **Type:** screen_crud
- **Typical size:** S
- **Description:** Users view and update their own profile, contact details and password.
- **Acceptance criteria:**
  - Given a logged-in user, When they change their mobile number, Then an OTP verifies the new number before saving.
  - Given a password change, When the new password violates the policy, Then it is rejected with the rule shown.
- **Variations that change size:** profile changes needing staff approval (M).

## Appointment / slot booking

- **Type:** workflow
- **Typical size:** L
- **Description:** Users book from available time slots defined by capacity per branch/resource; booking, rescheduling and cancellation with rules.
- **Acceptance criteria:**
  - Given a slot at full capacity, When a user tries to book it, Then it is shown unavailable.
  - Given a booking, When the user cancels less than 24 hours before, Then the system applies the late-cancellation rule.
- **Variations that change size:** fixed schedule only (M); waitlist and auto-fill (XL).

## Case / ticket tracking

- **Type:** workflow
- **Typical size:** M
- **Description:** Requests or complaints are logged, assigned, worked and closed with status history and a public tracking number.
- **Acceptance criteria:**
  - Given a new request, When it is submitted, Then a tracking number is issued and the requester can view status without logging in using the number and their email.
  - Given an assigned case, When it is resolved, Then the requester is asked to confirm closure.
- **Variations that change size:** SLA timers with escalation and auto-routing by category/location (L).

## Reference data maintenance

- **Type:** admin_config
- **Typical size:** S
- **Description:** Administrators maintain lookup tables (categories, offices, fee types) with active/inactive flags.
- **Acceptance criteria:**
  - Given an inactive category, When users create a new record, Then the category is not selectable but existing records still show it.
  - Given a change, When it is saved, Then it is audit-logged.
- **Variations that change size:** effective-dated values such as fee schedules (M).

## Fee assessment / computation rules

- **Type:** workflow
- **Typical size:** L
- **Description:** Compute fees or charges from a rule table (by type, size, location, penalties) and produce an assessment for review.
- **Acceptance criteria:**
  - Given an application type and declared values, When assessment is run, Then the fee breakdown is computed from the active rule table.
  - Given a late renewal, When assessed, Then the surcharge rule is applied and shown as a separate line.
- **Variations that change size:** fixed fee per type (S); admin-editable formula engine (XL).

## Legacy data migration

- **Type:** data_migration
- **Typical size:** L
- **Description:** Migrate existing records from spreadsheets or a legacy database with mapping, validation, rehearsal and reconciliation.
- **Acceptance criteria:**
  - Given the migration rehearsal, When it completes, Then a reconciliation report shows source vs target counts per entity.
  - Given rows that fail validation, When migration runs, Then they are written to a rejected-rows file with reasons.
- **Variations that change size:** single clean spreadsheet (S); several legacy systems with poor quality (XL).

## Data privacy consent and data subject requests

- **Type:** screen_crud
- **Typical size:** M
- **Description:** Capture consent at registration, show privacy notice, and handle data subject access/correction/erasure requests.
- **Acceptance criteria:**
  - Given a new registration, When the user has not ticked consent, Then registration cannot complete.
  - Given an access request, When the DPO approves, Then a downloadable export of the subject's personal data is generated.
- **Variations that change size:** consent only, no DSR handling (S).

## Inventory stock movement

- **Type:** workflow
- **Typical size:** L
- **Description:** Record receipts, issues, transfers and adjustments of stock per location with running balances.
- **Acceptance criteria:**
  - Given an issue larger than the on-hand quantity, When it is posted, Then it is rejected.
  - Given a transfer, When it is received at the destination, Then both locations' balances update.
- **Variations that change size:** lot/expiry tracking (+1 tier); barcode scanning on mobile (+1 tier).

## Availability and DR setup

- **Type:** nfr
- **Typical size:** L
- **Description:** Deploy for a stated availability target with backups, a DR environment, stated RPO/RTO, and a DR drill.
- **Acceptance criteria:**
  - Given the DR drill, When production is made unavailable, Then service is restored in the DR environment within the agreed RTO.
  - Given daily backups, When a restore test is run, Then data loss does not exceed the agreed RPO.
- **Variations that change size:** backup/restore runbook only (M).
